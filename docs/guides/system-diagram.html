System Architecture · Reference

SMSOne — a Spring Modulith behind a reactive edge

A multi-tenant platform: 26 domain modules inside one deployable, fronted by a stateless reactive API gateway that owns the edge. This page is the detail map — every filter in order, every limiter with its algorithm, every store with what actually lives in it, top to bottom.

01

The whole system, top to bottom

Clients enter through the gateway; the gateway shapes traffic and proxies /api/v1/** to the modulith over a load-balanced connection plus three secret-authed seams; the modulith turns the provider's token into its own identity once, then commits state and an event outbox in one transaction; async consumers fan out; every layer shares the stores at the bottom. Keycloak sits outside the box on purpose — it authenticates, it is not the user directory.

04

Inside the modulith — the request chain, exact order

The gateway already authenticated the token; the modulith re-validates it (defense in depth), turns it into its own identity once at −1, and then runs the rest of its ordered servlet chain — each filter one concern, each with a named refusal. Everything from −1 down keys on a person.id and an organization.id, never on an issuer's subject.

MAX_PREC RequestId — adopts the gateway's gw-… id (or mints one); it becomes meta.requestId in every envelope. headers
│▼
−100 Security chain — JWT resource server (Keycloak issuer, audience smsone-api); the credential is validated here and nothing more — who the caller IS is decided one stage down. Realm roles expand through the hierarchy (superadmin → admin → support); client roles stay namespaced by client id so a future client cannot mint a platform-admin. 401
│▼
−2 Impersonation — X-Impersonate: <session> swaps the effective principal; session validity re-checked every request; audit rows name the operator with onBehalfOf. 403
│▼
−1 Identity resolution — the one place a provider fact becomes a platform fact, and the reason Keycloak is swappable. (iss, sub) → external_identity → person.id (PersonLookup); the organization claim → external_organization → organization.id (OrgLookup); the membership's role → a permission set (OrgAuthorization). Below this line no module ever sees an issuer or a subject again. Every port is optional and every absence default-DENIES — shared must not compile-depend on the modules owning those tables, and an unanswerable question is not a yes. 3 DB readsmemoized/request
│▼ resolved BEFORE anything reads it
−1 Org MDC — stamps the effective org/tenant into the log context, so even a 429 two steps later is attributed. Shares the order with resolution and the tie is deliberately irrelevant: this filter only READS through the same provider, so whichever runs first performs the single resolution and the other is served the memo. logging
│▼
0 App rate limit — distributed window counters on Valkey, tenant-scoped keys, split policies: reads 600/min, writes 60/min (defaults). Second line behind the edge bucket — protects the DB tier even from inside traffic. 429Valkey
│▼
1 Idempotency — Idempotency-Key replays the stored response for same principal+key+body (24 h); same key, different body refuses. Claim-first with a takeover lease (fenced on the claim time). Keys are scoped per authenticated principal — person:<uuid> for a human, key:<uuid> for an API key, two id spaces that are never merged; an anonymous caller has no principal to scope by, so a permitAll route is simply not idempotent rather than sharing one bucket with every attacker. A replay still spends a rate-limit token (order 0 first) on purpose. 409Postgres
│▼
2 Provisioning gate — no-JIT: a valid JWT alone is not access; its subject must resolve to a provisioned person (INVITED is lazily activated to ACTIVE on the first real API hit). GET /api/v1/me is the one exception so onboarding is visible — method-scoped, and never lenient for a DISABLED account. Under an impersonation session it judges the TARGET, because the swap already happened at −2 — and does not activate them. 403 NOT_PROVISIONED
│▼
3 Org security policy — the tenant's own tightening: IP allowlist (CIDR, judging the client per app.http.trusted-proxy-hops — behind gateway/ingress the socket peer is OUR proxy, so XFF's proxy-vouched entry is the evidence), trusted-device requirement (X-Device-Id), session max-age, require-MFA (a human JWT must carry a multi-factor amr claim; API keys/impersonation are machine principals and exempt). Refusals name the rule; the policy endpoints themselves are always reachable (no lockout). 403 (named rule)
│▼
4 Maintenance — during a RESTRICT window the org's writes answer 503 + Retry-After; reads pass; ANNOUNCE is banner-only. 503
│▼
5 Subscription access — a PAUSED subscription (lapsed trial) makes the org read-only: org-scoped writes refuse, the billing surface stays open as the pay-to-recover path. 402 PAUSED
│▼
ctrl Controller — @PreAuthorize hasPermission(orgId, 'organization', '<perm>') fine-grained RBAC (permission union of role + groups, cached), entitlement gates with upgrade-shaped 403s, then the service layer. Every response: one JSON:API envelope, data ⊻ errors, always meta.requestId. envelope

Async plane — outbox, listeners, jobs

State change and event publication commit in the same transaction (Spring Modulith's JDBC event publication registry — a transactional outbox in Postgres). Listeners run after commit, async, each in its own transaction; an incomplete publication is re-delivered, so a consumer outage defers work instead of losing it.

TX Write + publish atomically — e.g. OrganizationRegistered, SubscriptionChanged, MemberRemoved land in event_publication with the domain rows. Postgres
│▼ after commit, async, at-least-once
consumer Webhook dispatcher — per-org subscriptions; payload signed HMAC-SHA256 (X-Webhook-Signature); at-least-once with backoff → dead-letter after max attempts (5); secrets AES-GCM at rest, full value shown once; delivery log per subscription; per-org retention override. → customer endpoints
consumer Exchange workers — imports/exports as jobs: batch-committed, resumable after a crash from the last committed batch, idempotent handlers (proven: 100k rows with a mid-run kill → exactly 100k effects); row-addressed error reports; cron schedules run as their owner. S3 + Postgres
consumer Billing listeners — on org registration: auto-provision the Kill Bill account (idempotent, race-safe) and start the trial-on-signup (PRO 30d, skipped if a plan was already assigned). Kill Bill pushes payment/subscription events back → reconcile into entitlements (the one write direction). Kill Bill
consumer Search indexer · notifications — projections into Postgres FTS; in-app + email/SMS sends resolved through the integration hub's effective provider (org override wins over platform default). Postgres · SMTP
│ scheduled, cluster-locked
jobs Scheduler — DB lock rows make every job single-flight across instances (observable at /admin/scheduler/locks): trial expiry (TRIALING → PAUSED), retention purges (webhook deliveries, exchange jobs, soft-deleted rows — per-org overrides honored, legal holds always skipped), billing reconcile. Webhook delivery — the full state machine

One durable row per (event × matching subscription), driven by a competing-consumer worker pool. Delivery is at-least-once — a crash between the POST and its status write leaves the row claimed, and the stale-lock reclaim re-POSTs it — so receivers verify the signature and de-duplicate on their side.

stateDiagram-v2
  [*] --> PENDING : event commits → one row per matching subscription (single batch INSERT)
  PENDING --> PROCESSING : claim — FOR UPDATE SKIP LOCKED batch,
joined with the subscription's URL + signing secret
  PROCESSING --> DELIVERED : receiver answers 2xx
  PROCESSING --> PENDING : transient failure (5xx · timeout · DNS)
reschedule at now + 10s × 2^(n−1), cap 1h
  PROCESSING --> DEAD : permanent failure (4xx) — immediately
or attempts reach max (5)
  PROCESSING --> PENDING : crash mid-POST → lock stale (2 min)
→ reclaimed and re-POSTed (at-least-once)
  DELIVERED --> [*] : purged at retention (30d default, per-org override)
  DEAD --> [*] : dead-letter — visible in the delivery log

Exchange jobs — imports & exports at scale

Never a long request: submit answers 202 with a job id and a worker drives the file through batches. The batch commit is the whole trick — records, offset, counters, heartbeat, and the cancel check are one transaction, which is what makes a crashed job resumable and an at-least-once re-run produce exactly-once effects (proven: 100k rows with a mid-run kill → exactly 100k effects).

stateDiagram-v2
  [*] --> PENDING : submit → 202 + job id (source already in S3)
  PENDING --> VALIDATING : claimOne — stale-lock 5 min
  VALIDATING --> PROCESSING : header matches the handler's template
  VALIDATING --> FAILED : unreadable file / wrong header — curated message
  PROCESSING --> PROCESSING : batch of 500 → ONE tx commits records + next_offset +
processed/failed counters (the write IS the heartbeat,
and returns cancel_requested)
  PROCESSING --> COMPLETED : all records applied, failed = 0
  PROCESSING --> COMPLETED_WITH_ERRORS : invalid rows collected —
row-addressed CSV report (302 from /report)
  PROCESSING --> PENDING : infra error → release claim, backoff base × 2^(n−1)
→ later claim RESUMES from next_offset
  PROCESSING --> FAILED : claim generation hits max (3) — a poison batch dies loudly
  PROCESSING --> CANCELLED : cancel_requested seen at the batch boundary

Exactly-once effects

at-least-once × idempotent
resumea reclaimed job restarts from the last committed offset, never row zero
handlersidempotent by contract — re-applying a delivered batch is a no-op
data errorsinvalid records go to the error table (on conflict do nothing — re-runs don't duplicate) and never burn a retry
infra errorsrelease + exponential per-claim backoff; 3 claim generations then FAILED

Liveness & fencing

competing consumers
heartbeatmid-batch re-stamp (~every staleLock/3) keeps a slow batch from being double-claimed; a false return means the claim was lost — stop immediately
cancelbest-effort, honored at the next batch boundary — mid-batch records still commit
cadencepoll 2 s · batch 500 · stale lock 5 min · presigned results 10 min

Billing — the reconcile loop

Kill Bill owns the money; the subscription module owns access. Every state that matters flows one way — Kill Bill event → reconcile → the audited plan-assign path — and reconcile is idempotent by construction: it repeats what Kill Bill says, so a duplicate callback or a dev setup without the callback converges to the same standing.

stateDiagram-v2
  direction LR
  state "FREE (no row)" as FREE
  [*] --> TRIALING : org registered → trial-on-signup (PRO, 30d, entitlement-only)
  [*] --> ACTIVE : straight-to-paid (admin assign / subscribe)
  TRIALING --> PAUSED : TrialExpiryJob — trial lapsed unpaid
  TRIALING --> ACTIVE : payment lands / plan assigned
  PAUSED --> ACTIVE : payment success (callback) or admin assign — the pay-to-recover path

  PAST_DUE --> ACTIVE : payment success (callback or a COMPLETED collection)

  note right of PAUSED : org is READ-ONLY — org writes answer 402,\nreads pass, /billing stays open

Two gateway adapters behind one internal seam, each with a switchable mode (sandbox default — nothing touches real money until live is explicit; credentials resolve hub-first with env fallback, and the mode is stamped on every payment row). The only sanctioned crossing between the platform axis and tenant data. A session is a first-class record with a hard clock, worn per-request via a header — and its validity is re-checked on every request, deliberately uncached: ending a session must bite immediately, not a TTL later.

The shared kernel cache behind entitlements, permissions, and settings: per-node Caffeine L1 in front of shared Valkey L2, built so an L2 outage degrades and a write invalidates every node now — a plan downgrade must bite the very next gate check.

Data & caching plane — what lives where

Five stores, each with one job — plus a two-level cache in front of the hot reads.

Postgres 18

system of record
  • Every module's tenant data — 54 tables, 50 Flyway migrations, one schema
  • person + person_contact — the canonical identity; external_identity / external_organization are the only tables holding an id minted by a provider
  • event_publication — the transactional outbox
  • Full-text search: websearch_to_tsquery + pg_trgm typo fallback (p95 ~35ms @ 100k docs)
  • Soft deletes + nightly purge at retention (legal holds skip)
  • Scheduler lock rows — clustered single-flight jobs

Valkey 8

  • Edge token buckets — SCG rate limiter (20/s, burst 40)
  • gwquota:<tenant> — plan-quota fixed windows
  • App rate-limit windows — per-tenant read/write counters

  • L2 cache + pub/sub invalidation channel (below)

SeaweedFS

  • Personal + org files, document catalogs

Kill Bill 0.24 + MariaDB

billing engine · kaui :29095

  • Catalog plans pro-monthly / enterprise-monthly; subscriptions → invoices → payments
  • Push notifications → /api/v1/billing/killbill/notifications → reconcile standing (ACTIVE ↔ PAST_DUE) into entitlements
  • Payment methods via KB plugins — raw card data never touches the platform

DuckDB (embedded)

analytics mart
  • In-process OLAP — a durable mart file shared by all in-process connections
  • Rebuilt on a TTL, not per call: a mart older than app.analytics.mart-ttl (15 min) is re-materialized on the next read, so a report may lag Postgres by up to that interval. One refresh per report is ever in flight; callers arriving during it wait rather than read the mart it is replacing
  • Staging table + atomic swap: a failed refresh leaves the previous mart serving, and the built-at stamp is written only after the swap
  • Long refreshes run on their own connection so KPI reads never block
  • Curated report catalog surfaced at /api/v1/analytics/reports

Keycloak 26 (its own store)

one provider's data
  • Realm smsone imported at boot (displayName ← BRAND_NAME)
  • Its users (pinned platform admin), its Organizations per tenant, realm roles
  • Not the user directory. person in Postgres is; this store holds one provider's accounts, and external_identity/external_organization are the only two tables over there that reference anything in here
  • Dev-mode store lives in-container — a recreate re-imports the realm

The two-level cache (shared kernel, backing entitlements, permissions, settings…): L1 is per-node Caffeine, L2 is shared Valkey; a pub/sub invalidation channel drops peer L1s on write; L2 failure degrades to L1-only (never an outage); striped locks bound the stampede on cold keys.

read L1 Caffeine (per node, ns access) → miss → L2 Valkey (shared; first node to load publishes, peers' cold reads hit L2 not the DB) → miss → loader (DB) under a striped lock → write-through L2 then L1. hit path
write Invalidate — evict + publish on the invalidation channel → every other node drops its stale L1 entry; a plan change bites the very next gate check, not a TTL later. pub/sub

Postgres-first, and portable by seam. The system of record is PostgreSQL by design — the schema leans on it for real capability (soft-delete partial indexes, lock-free SKIP LOCKED queue fan-out, native FTS). It is not a portable lowest-common-denominator schema, and that is deliberate. A product built from the template on Oracle / SQL Server / MySQL is a bounded port, not a rewrite: ~90% of the code is DB-agnostic and the Postgres-isms are confined to five seams.

Every request the edge serves becomes, eventually, a billable usage record — through a buffer that never blocks the hot path, a signed internal seam, an additive daily ledger, and an opt-in export that Kill Bill de-duplicates by tracking id. Each hop is at-least-once; the ledger's upsert and the export's tracking id are what make the whole pipeline effectively exactly-once.

Why it cannot lie

failure math
flush failsthe drained counters are restored into the buffer — counted again next minute, never lost (gateway crash loses ≤60s of counts: the accepted trade)
report replaysthe upsert is additive per (org, day) — but a report is sent once per drain, so replays don't double: the seam retries only on failure, where nothing was added
export replaysKill Bill rejects a duplicate trackingId — the export can crash after the push and re-run safely; exported flips only after acceptance
unknown orgsnon-UUID tenants (IP-keyed anonymous traffic) are skipped at the seam — the ledger holds orgs, not noise

MCP — the agent surface

A second protocol surface for AI agents — JSON-RPC 2.0 over stateless streamable HTTP at POST /mcp (a servlet, not an MVC controller) — over the same module ports the REST controllers call.

Org-implicit by construction: no tool takes an orgId — the org comes from the API key — and discovery is permission-filtered (tools/list shows only what the key may call; a hidden tool still refuses on a direct call, fail-closed). 35 tools, 2 prompts, 3 smsone:// resources; the deep dive is docs/guides/mcp-guide.html.
