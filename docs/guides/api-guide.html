SMSOne · API Guide for Testers
Swagger UI OpenAPI

How to read this. Every endpoint is one block: the method, the path, and — on the right — who can call it. Access runs on two disjoint axes, so the chip tells you which one and never mixes them:

any caller — any signed-in user, for their own data (the Shared axis) platform-admin — a Keycloak realm role (support → admin → superadmin) member:invite — an organization permission, inside one tenant

A platform role grants zero org permissions and vice-versa — the only sanctioned crossing is impersonation. Paths use {orgId} for the tenant id.

A · Before you call anything

The five things true of every request: how you authenticate, the shape you always get back, how lists page, how you get rate-limited, and how to make writes safely retryable.

A1 · Authentication & the two axes

Every call carries a bearer token from the platform's identity provider (Keycloak in this deployment), minted for this API (audience smsone-api). Dev shortcut: make token or scripts/api.sh (which also encodes page[...] for you).

# raw password grant (dev realm) → an access token
curl -s $BASE/realms/smsone/protocol/openid-connect/token \
  -d grant_type=password -d client_id=smsone-web \
  -d username=paul -d password=Paul123 | jq -r .access_token

# then send it on every call
curl $BASE/api/v1/me -H "Authorization: Bearer $TOKEN"
Machine access uses X-Api-Key: <prefix>.<secret> instead of a bearer (see Org API keys). Impersonation adds X-Impersonate: <sessionId> to a tenant call (see Users & impersonation). Never combine axes in one credential.
The token says who an issuer thinks you are; it is not your identity here. Keycloak is one authentication adapter, not this platform's user directory. Every request resolves the token's (iss, sub) pair through the external_identity link table to a person.id, and the token's organization claim through external_organization to an organization.id — once, before any controller runs. Past that point every id you see on the wire is in this platform's own id space, and no provider identifier appears in a path or a body anywhere in this guide. That is the point of the indirection: adding or swapping an identity provider is rows in those two tables, not a new API.
Org-scoped tokens. Tenant calls need the token's organization claim to resolve to the org named in the path — and the path carries organization.id, the platform's own tenant key. A token scoped to org A gets 403 on org B even if you belong to both. Switching orgs = requesting a new token scoped to the other; the server never trusts a client-asserted active org. An org alias is never an org id: resolution runs through the link table in both directions, so a token scoped to one tenant cannot address another whose slug happens to collide.

No-JIT: a valid JWT alone is not access — the subject it carries must already be linked to a provisioned person, or you get 403 ACCOUNT_NOT_PROVISIONED. A token that validates perfectly and resolves to nobody is exactly the case this refuses: proving who an issuer thinks you are has never been permission to create an account here. GET /api/v1/me is the one gate exception (so you can see your own onboarding status).

A2 · The response envelope & errors

Every JSON response is one envelope — data xor errors, always meta.requestId (also the X-Request-Id header; quote it in bug reports).

{ "data": { "id": "org.example", "type": "setting", "attributes": { "key":"org.example", "value":"42" } },
  "meta": { "requestId": "01J4X9GVJ4C1T4V0V3S8B7NQZD" } }

{ "errors": [ { "status":"422", "code":"VALIDATION_FAILED", "title":"Validation failed",
                "detail":"cron must be a valid six-field Spring cron expression.",
                "source": { "pointer":"/data/attributes/cron" } } ],
  "meta": { "requestId": "01J4X9…" } }
  • Prefer RFC 9457? Send Accept: application/problem+json — same data, standard shape.
  • Localized details: send Accept-Language: fr; when the catalog holds error.<code> the detail localizes, else you get the English original.
  • Stack traces never reach the wire — a 500's detail is generic; the trace lives in the server log under your request id.

A3 · Cursor pagination

Collections page by keyset cursor — no page numbers, no totals (by design). Parameters are literally page[size] and page[after] (encode the brackets, or let scripts/api.sh do it).

ParamInReqDescription
page[size]querynoRows per page (default 20). No total count is ever returned.
page[after]querynoOpaque cursor from a previous page's meta.page.nextCursor / links.next.

A4 · Rate limits & plan quotas

There are two rate controls in front of you, at different layers, protecting different things. Both answer 429, but for different reasons — so they speak through different headers, and each calls for a different response. Treat them separately.

 Edge burst limiterPlan quota
Triggers whenA single caller exceeds the short-term request rate.An organization exceeds the volume its subscription allows.
PurposeProtect the platform and backends from traffic spikes (burst-smoothing), applied to every caller.Enforce the subscription tier and share capacity fairly across tenants.
Measured overSeconds — a token bucket: ~20 requests/second sustained, burst of 40.A fixed window — e.g. 600 reads/min, 60 writes/min, per plan.
ScopePer caller (principal, else tenant, else IP).Per organization, by subscription tier.
HeadersX-Edge-RateLimit-Remaining · -Burst-Capacity · -Replenish-RateX-RateLimit-Limit/Remaining/Reset + draft-IETF RateLimit / RateLimit-Policy
Recommended responseReduce the request rate; retry after Retry-After.Wait for the window, or upgrade the plan; the response carries the RATE_LIMITED envelope and Retry-After.

The two limits are complementary (defense in depth): a caller within its plan allowance is still held to the per-second edge limit, and a caller within the edge burst is still held to its plan's per-window allowance. Because the headers are namespaced, a client can determine which limit it reached.

# A normal 200 through the gateway carries BOTH sets — they never collide:
X-RateLimit-Limit: 600     X-RateLimit-Remaining: 599     RateLimit: "read";r=599;t=60     ← plan quota
X-Edge-RateLimit-Remaining: 39     X-Edge-RateLimit-Burst-Capacity: 40                      ← edge burst bucket

# Edge burst 429 — the caller exceeded the burst rate; reduce the rate and retry shortly:
HTTP/1.1 429     Retry-After: 1     X-Edge-RateLimit-Remaining: 0

# Plan quota 429 — the plan's allowance for this window is exhausted; wait or upgrade:
HTTP/1.1 429     Retry-After: 30     RateLimit: "read";r=0;t=30
{ "errors": [ { "code":"RATE_LIMITED", "detail":"Rate limit exceeded for 'read'. Retry after 30s." } ] }
How to react in code. Always honour Retry-After. Repeated edge-limit responses (X-Edge-RateLimit-*) indicate bursty traffic — add client-side pacing or exponential backoff. Repeated plan-quota responses (X-RateLimit-* / RateLimit) indicate the subscription ceiling — spread work across the window, or upgrade the plan.

Automatic retries (safe methods only)

Independent of rate limiting: when a backend fails transiently with a 5xx, a route configured for retries has the gateway retry it automatically — GET requests only (up to three attempts, then it returns the error). Write methods are never retried automatically, because replaying a POST, PUT, or DELETE may duplicate a side effect. To make a write safely retryable, send an Idempotency-Key: a retry then replays the stored response rather than executing the operation again.

A5 · Idempotency keys

Any unsafe request may carry Idempotency-Key: <your-uuid>. Same principal + same key + same body ⇒ the stored response replays; same key with a different body ⇒ 409. Keys live 24h.

B · You — anything a signed-in user does for themselves

The Shared axis: no platform role, no org permission — just any caller acting on their own account. This is where every tester starts.

B1 · Who am I

GET/api/v1/meany caller

Your identity, effective roles (already tier-expanded), active org, and provisioning status. The one call that works while INVITED — so you can see your own onboarding.

{ "data": { "id":"5862…", "type":"user", "attributes": {
    "personId":"5862…", "email":"you@acme.test",
    "name": { "formattedName":"Dr. Ada Lovelace-Byron MBE", "givenName":"Ada",
              "familyName":"Lovelace-Byron", "honorificPrefix":"Dr.", "preferredName":"Addy" },
    "roles":["platform-admin","USER","platform-support","platform-superadmin"],
    "activeOrgId":"6a1f…", "provisioningStatus":"ACTIVE" } } }

Four roles from two grants: platform-superadmin + USER — the hierarchy expands superadmin → admin → support. It shows your effective tiers, not four separate grants.

The resource id is your person.id; personId repeats it as a typed field and is null exactly while provisioningStatus is UNPROVISIONED — those are the two states onboarding branches on, so a client should not have to infer one from the resource id. Before provisioning there is no person to name and the id falls back to your own token subject. There is no activeOrgAlias any more — the alias belongs to the organization resource that activeOrgId now names directly, so GET /api/v1/orgs/{activeOrgId} is the honest way to get it.

name is the SCIM/OIDC name block and is always an object — {} for anyone this platform was never told a name for, which is an ordinary state and not an error. Null components are omitted entirely, so test for the key, never for a null value. The seven keys are formattedName, givenName, familyName, middleName, honorificPrefix, honorificSuffix, preferredName — the same names SCIM 2.0 and OIDC use, so a client that already speaks either does not translate.

email comes from your person_contact book, not from the token: the address this platform can reach you at, which need not be the one your provider put in the JWT. It is the best address on file, so it changes when you prove a new address or re-point your primary — see B2 · Contact addresses. It is absent when nothing is on file.

formattedName is never derived from the parts — not composed, not as a fallback. This is the single thing an integrator is most likely to get wrong. Name order is cultural (given-then-family is one convention among several) and mononyms are ordinary, so the display value is supplied whole or it is absent, and the client decides what to render when it is absent. Falling back to givenName + " " + familyName shows a large part of the world their own name backwards; falling back to the e-mail is right. The server never assembles one either: patch the parts and formattedName stays exactly as it was until you send it explicitly.

Values are trimmed. An over-long component is 422 VALIDATION_FAILED with source.pointer naming the field. A body of {} is a legal no-op (200), and a patch that changes nothing writes nothing — no version bump, no audit row. A machine key (X-Api-Key) gets 403: a credential has no name.

Why PATCH-with-a-map, and what the four cases mean. Seven mostly-nullable fields behind a PUT means any client that omits honorificSuffix silently erases it — so the shape here is a partial map where key presence is the instruction:
You sendWhat happens
key absentUnchanged. Send only what you are changing.
"key": nullCleared. The explicit null is the only way to erase a component.
"key": "" or whitespaceCleared, same as null — whitespace is not a name, so nothing stores a space.
{}Legal no-op — 200 with the name as it stands.
an unknown keyRefused — 422 VALIDATION_FAILED, source.pointer = the offending key.
That last row is the point of the design: a typo'd familyname that quietly did nothing would look exactly like a save that worked. The same body, the same semantics and the same person-name response serve the operator's PATCH /api/v1/admin/users/{personId}/name — one operation, two callers.

B2 · Contact addresses (where the platform reaches you)

Your own contact book — the addresses this platform may send to and resolve you by, one row each in person_contact. Everything here is about a single rule, and every response below is a face of it:

An unverified address is inert. Nothing resolves you by it, no invite matches it, it can never be your primary, and the platform will never fall back to it. It is a claim until somebody proves it — which is why you may freely add an address another account also holds (you get 201, on purpose: refusing would turn this endpoint into an oracle for "does this address have an account here?"). The collision is settled at verification, where exactly one account can win.

Attributes of a contact resource: kind (EMAIL · PHONE · OTHER), value, label (yours, optional), primary and verified (both booleans, both always present), verifiedAt and createdAt (ISO-8601 instants). Nulls are omitted from every payload in this API, so verifiedAt is simply absent while unproven — branch on verified, never on the presence of verifiedAt. These are person-scoped: a machine key (X-Api-Key) gets 403, because a credential has no mailbox.

GET/api/v1/me/contactsany caller

Every address on file for you, best first within each kind: primary, then proven, then oldest.

{ "data": [
    { "id":"9f2c…", "type":"contact", "attributes": {
        "kind":"EMAIL", "value":"ada@acme.test", "label":"work",
        "primary":true, "verified":true, "verifiedAt":"2026-08-06T09:12:44Z",
        "createdAt":"2026-07-30T11:02:07Z" } },
    { "id":"1b70…", "type":"contact", "attributes": {
        "kind":"EMAIL", "value":"ada@personal.test",
        "primary":false, "verified":false, "createdAt":"2026-08-06T09:10:01Z" } } ],
  "meta": { "requestId":"01J4X9…" }, "links": { "self":"/api/v1/me/contacts" } }
This one list does not page — no page[size], no page[after], no meta.page, no links.next. A3's keyset rule exists to stop unbounded scans, and this collection cannot grow one: it is capped at 10 addresses per kind. A cursor here would be ceremony no client would ever page through. (Same shape, same reasoning, as the payment-methods list.)

Why primary outranks verified in the ordering: primary is what you (or the admin who invited you) chose, and honouring a verified-but-unchosen address would quietly redirect your mail. Verified breaks the tie underneath.

POST/api/v1/me/contacts/{id}/verificationany caller

Prove an address. No request body — the proof is your own token, which must carry email_verified: true and an email claim equal (case-insensitively) to this contact's value.

This platform sends no verification message. There is no e-mailed challenge in this slice; the proof is the identity provider's, already sitting in your token. So proving a new address is a four-step dance, and a client that offers a "resend verification" button is promising something that does not exist:
  1. add it here (POST /api/v1/me/contacts);
  2. change the e-mail on your Keycloak account console;
  3. complete the confirmation Keycloak mails you;
  4. sign in again so the fresh token carries it — then call this.
POST /api/v1/me/contacts/1b70…/verification        # no body; Bearer token does the talking
# → 200
{ "data": { "id":"1b70…", "type":"contact", "attributes": {
    "kind":"EMAIL", "value":"ada@personal.test", "primary":true, "verified":true,
    "verifiedAt":"2026-08-06T09:12:44Z", "createdAt":"2026-08-06T09:10:01Z" } } }

Note primary flipped to true without being asked. The first proven address of a kind takes the primary flag, retiring the unproven placeholder your invite left — the platform stops preferring an address nobody established over one somebody did. A proven primary is a choice and is never overridden; that is what the next endpoint is for.

PUT/api/v1/me/contacts/{id}/primaryany caller

Choose the address of that kind the platform prefers. No request body. Exactly one primary per (person, kind) — the previous one silently loses the flag.

PUT /api/v1/me/contacts/1b70…/primary   → 200  {"data":{…,"attributes":{"primary":true,…}}}

Idempotent (already primary ⇒ 200, unchanged). 404 RESOURCE_NOT_FOUND for an unknown id or one that is not yours. 409 CONFLICT — "Verify this address before making it your primary one." A refusal never stands your current primary down: the check runs before the flag moves, so a 409 here cannot leave you with no primary at all.

DELETE/api/v1/me/contacts/{id}any caller

204 No Content, no body. A soft delete — and the address is immediately free for another account to claim and prove. Removing your primary automatically promotes the best remaining verified contact of that kind.

404 RESOURCE_NOT_FOUND for an unknown id or one that is not yours. The 409s below are EMAIL only — a phone number reaches nothing and resolves nobody, so PHONE/OTHER always delete:

GuardCONFLICT detail
Reachability"This is the only address the platform can reach you at — add another first."

The third guard is the interesting one, and it is why "add an address, delete the rest" is not a way to point this platform's outbound mail at a stranger: a self-added claim can only become your best address by outlasting every primary and every verified one, so the API refuses to let the last of those go.

Audit actions written by this surface: identity.contact_added, identity.contact_verified, identity.contact_primary_changed, identity.contact_removed — all with target = your person.id.

C · Operating the platform

The Platform axis — a Keycloak realm role, hierarchical: platform-support (read) → platform-admin (change) → platform-superadmin (escalate). These surfaces manage tenants and the platform itself, never a tenant's data directly (that's impersonation).

C2 · Users & impersonation

GET/api/v1/admin/usersplatform-support

Every person on the platform, across every tenant (cursor-paginated). …/{personId}/profile reads one, …/{personId}/devices lists their registered devices. Rows carry personId, name, email and status (INVITED → ACTIVE → DISABLED).

Breaking change: attributes.formattedName is gone, replaced by the nested attributes.name block — the same seven-component SCIM/OIDC object GET /api/v1/me returns, with null components omitted and {} for a person no name was ever supplied for. A client still reading attributes.formattedName now reads undefined; it wants attributes.name.formattedName. The whole block travels rather than the lone display value because an operator about to fix a typo needs to see the component the typo is in — being shown only the display value and then asked to patch givenName blind is how a correction lands on the wrong field.
{ "data": [ { "id":"5862…", "type":"user", "attributes": {
      "personId":"5862…", "email":"ada@acme.test", "status":"ACTIVE",
      "name": { "formattedName":"Dr. Ada Lovelace-Byron MBE", "givenName":"Ada",
                "familyName":"Lovelace-Byron", "honorificPrefix":"Dr." } } } ],

                       "sessionMaxAgeSeconds":3600,"requireMfa":true}
POST …/security-policy/trusted-devices {"personId":"5862…","deviceId":"…","trusted":true}   # trust is the org's grant

ipAllowlist judges the real client, not the proxy in front: the platform declares its proxy depth (TRUSTED_PROXY_HOPS — 0 direct, 1 behind the gateway, 2 behind ingress + gateway) and only the proxy-vouched X-Forwarded-For entry is believed; a caller-forged entry buys nothing. Platform-wide IP blocking is separate and earlier — the gateway's deny-list refuses hostile sources before authentication.

requireMfa holds human sessions to a multi-factor token — the JWT's amr claim must name a second factor (otp/totp/webauthn…), else 403 (mfa). API keys are machine credentials and exempt; new invites into a require-MFA org get TOTP enrollment added to their first-login link (CONFIGURE_TOTP).

PUT/api/v1/orgs/{orgId}/integrationsorg:update

An org override for a provider kind — wins over the platform default (C5), which wins over env config. This is how orgs opt for different providers: SMS_PROVIDER → speedamobile (settings apiId/apiPassword/senderId; notifications route each SMS by the recipient org's choice) · PAYMENT_GATEWAY → pesapal | yo-uganda (settings include mode: sandbox|live and the gateway credentials; also sets the org's default payment provider, D5). Secrets encrypted + masked; POST …/integrations/{id}/test probes it.

PUT /api/v1/orgs/{orgId}/integrations
{"kind":"PAYMENT_GATEWAY","provider":"yo-uganda","settings":{"mode":"live","apiUsername":"…","apiPassword":"…"}}

D7 · Documents, search, support, audit & maintenance

POST/api/v1/orgs/{orgId}/documentsdocument:manage

Org document catalog (multipart file). GET …/{id} 302s to a presigned URL; DELETE drops the bytes but the metadata row soft-remains (the trail). Exchange artifacts appear here with source:"EXCHANGE".

GET/api/v1/orgs/{orgId}/search?q=search:query

Ranked full-text (with trigram fallback for typos), tenant cut inside the SQL. Platform-wide search is /api/v1/admin/search (platform-support).

POST/api/v1/orgs/{orgId}/ticketsticket:write · reads ticket:read

Open + converse on your support tickets (GET …/{id}/messages — cursor-paged, oldest first; public messages only, and the internal notes are excluded by the query rather than hidden after it). The platform side is C4.

GET/api/v1/orgs/{orgId}/auditaudit:read

Your tenant's own trail; filter action/from/to. Every row carries actorPersonId — the accountable human, and null when there is none (a scheduled job, or a machine key: that is an answer, not a missing value). Rows written during an impersonation put the operator in actorPersonId and the worn person in onBehalfOfPersonId, with impersonationId pointing at the session that carries the stated reason. target stays free text — it is polymorphic, so what it holds (a person id, a role code, a setting key) is read through action. Read the maintenance banner at GET …/maintenance?active=true.

Unchanged by the schema split, and it is the endpoint that stays whole: your organization's rows are your organization's, wherever they are stored. Rows that belong to no tenant were never here and are on the platform trail (C4) instead.

D8 · Geolocation

POST/api/v1/orgs/{orgId}/geo/stampsgeo:capture

Attach a device location to any record via a polymorphic subject (subjectType+subjectId — a soft reference, no FK). Subject here is the stamped record, not an identity — it holds a person id only on person-shaped rows. Validated against the record-type's capture policy: coordinate range, minimum accuracy, freshness, and allowed source. Coordinates are plain lat/lng (no PostGIS); who captured it is resolved from the caller into capturedByPersonId, like the audit log — null for a machine or unauthenticated capture.

GET/api/v1/orgs/{orgId}/geo/stampsgeo:read

Stamps newest first, filtered by subject (subjectType+subjectId) or a bbox=minLat,minLng,maxLat,maxLng. Exact coordinates need geo:read_precise; geo:read alone returns them coarsened to ~1.1 km. Cursor-paginated (page[size]/page[after]).

GET/api/v1/orgs/{orgId}/geo/policies/{subjectType} · PUT …geo:policy:manage

Configure whether a record-type captures a location: OFF, OPTIONAL, or REQUIRED (a REQUIRED type rejects a record with a missing or too-coarse fix), plus min-accuracy, freshness, allowed sources, and retention. GET reads it (default OFF); PUT upserts it.

E3 · Data layer & database portability

You never touch the databases directly, but here is what stores what — and how the template ports to another RDBMS if a product built from it requires one.

StoreRole
PostgreSQLSystem of record — every module's data, the transactional outbox, full-text search, soft-delete and retention, and the durable-queue tables. Split across two schemas: platform for what belongs to the installation (people, the org registry, catalogues, framework tables) and tenant_pool for what belongs to a tenant. Each request is pointed at one of them before any controller runs; seven tables exist in both. See below.
ValkeyShared fast state — the L2 cache with pub/sub invalidation, rate-limit windows, idempotency snapshots (24 h), and the durable IP-block and route stores.
SeaweedFS (S3)File and document bytes, and exchange artifacts. Reads hand out short-lived presigned URLs, so bytes never proxy through the application.
DuckDB (embedded)Analytics marts behind /api/v1/analytics/reports — in-process OLAP, kept off the transactional path. Each mart is rebuilt on a TTL (app.analytics.mart-ttl, 15 min), so reads are cheap and may lag Postgres by up to that interval.
Kill Bill → MariaDBThe billing engine's own store (invoices, subscriptions, payments), reconciled one-way into entitlements.
Keycloak → PostgresOne authentication provider's own store (its users, its organizations, realm roles). Not this platform's user directory: person is, in the Postgres above, and external_identity / external_organization are the only two tables permitted to hold an identifier minted over here.
Two schemas, and what a tester can actually observe. A tenant's rows and the platform's rows live in different schemas of the same database, and the connection serving a request is pointed at exactly one of them before any controller runs — so an unqualified read can only land in the schema this request was routed to. Almost nothing about the API changes: same paths, same payloads, same permissions.
  • The one visible change is GET /api/v1/audit — un-filtered, it is now the platform-level trail rather than everything; ?org= reads one tenant.
  • A credential naming no organization on an /api/v1/orgs/{orgId}/… route is refused up front with a 403 (E1) instead of dying deeper in.
  • Nothing else moved: org-scoped endpoints answer exactly as before, and no id, field or status code changed.

The point of the separation is portability of a tenant, not extra isolation inside one database — a tenant that lives in its own schema can be dumped and restored whole, with no WHERE org_id = ? to get wrong. That is also why every tenant query still carries its org_id predicate: while tenants share a pooled schema, that predicate is what separates them.

PostgreSQL-first, by design. The system of record is PostgreSQL, and the schema uses Postgres for genuine capability — soft-delete partial indexes, lock-free SKIP LOCKED queue processing, and native full-text search. This is the intended default: in a SaaS deployment, the platform owns its database.

Porting to Oracle, SQL Server, or MySQL. Building a product from this template on a different RDBMS is a bounded task, not a rewrite. Roughly 90% of the code is database-agnostic; the Postgres-specific code is confined to five seams — the SKIP LOCKED queue claims (already isolated behind a DbDialect bean), the ON CONFLICT upserts, native full-text search, and the migration types and partial indexes. The complete seam map, a per-vendor SQL translation table, and the step-by-step procedure are in docs/PORTING.md. For the deepest coupling (search), the recommended approach is to replace the search adapter with OpenSearch or Elasticsearch — it already sits behind a port — rather than reimplement full-text search per vendor.

F · Agents (MCP)

The platform's agent surface: a Model Context Protocol server at /mcp — a second protocol surface over the same services, with permissions identical to REST. Everything in Parts A–D about who may do what still applies; this part covers what an agent sees. Deep dive: the MCP guide.

F1 · Connecting an agent

POST/mcpAPI key (org)

JSON-RPC 2.0 over stateless streamable HTTP — one endpoint, no session to keep alive. Authenticate with an org API key (D2), spelled either X-Api-Key: sk_… or Authorization: Bearer sk_… — both tiers understand the bearer form, and JWTs still work.

# Claude Code — .mcp.json
{ "mcpServers": { "smsone": {
    "type": "http", "url": "http://localhost:28090/mcp",

Claude API: list the server under mcp_servers with authorization_token set to the key (it arrives as Bearer sk_…). Managed Agents: store the key in the vault as a static_bearer credential. Claude Desktop / claude.ai custom connectors: just add the URL — the client discovers Keycloak via /.well-known/oauth-protected-resource, runs the browser consent, and calls with a JWT whose mcp scope stamps the smsone-mcp audience (tokens without it — a web login, say — are refused at /mcp). Full connect recipes, diagrams and the OAuth flow live in the MCP guide.

Tools are org-implicit. No tool takes an orgId — the org comes from the key. tools/list is filtered to what the key's permissions allow, and a hidden tool still denies on a direct call — discovery is a convenience, never the enforcement. The five area surfaces (tickets, exchange, search, subscription, usage) gate on their own codes since V48 — a key minted before then holds none of them and must be re-minted (or have the codes appended) to keep seeing those tools.

F3 · Conventions & guardrails

The REST contract restated in MCP terms — nothing here is a new rule, only the same rules on a second wire.

  • Request id everywhere — every result and every error carries _meta["smsone/requestId"]; quote it in bug reports exactly like meta.requestId (A2).
  • Same error vocabulary — tool errors name the REST error codes (FORBIDDEN, VALIDATION_FAILED, RATE_LIMITED…), so one runbook serves both surfaces.
  • Cursor pagination — collections take page_size / page_after (max 100) and return the next cursor: the same keyset model as A3, spelled tool-argument style.
  • Write guard — WRITE/DESTRUCTIVE tools refuse during a RESTRICT maintenance window (SERVICE_UNAVAILABLE) and while the subscription is paused (SUBSCRIPTION_PAUSED); READ tools pass.
  • Attribution is a person, or nobody — the org comes from the key, but a person does not: an API key acts for no human, so whoami reports personId: null and the tools whose table demands an accountable human (the support desk) refuse the key outright rather than invent a synthetic identity. An OAuth-connected agent runs as a real person.id and passes. This is the intended answer, not a gap.
  • Org security policy applies — the org's IP allowlist (D6) judges MCP calls too.
  • Secrets shown once — webhook_create / webhook_rotate_secret return the signing secret in that result only, exactly like the REST endpoints.
  • Async pattern — exchange_submit → poll exchange_job_get → exchange_result_url; never a long-running call.
  • Audited + measured — every mutation lands in the audit trail as mcp.tool_invoked; metrics smsone.mcp.tool.calls{tool,kind,outcome} plus a duration timer.
  • Kill switch — app.mcp.enabled=false refuses every call with a named JSON-RPC error (-32050), leaving REST untouched.
  • Edge policy — the gateway route mcp-api runs policy edge-mcp: authenticated, rate-limited, 60 s response timeout, 2 MiB body cap. Inside, the modulith applies rate-limit tier mcp — a per-key bucket, 300/min default.

Beyond tools, the server publishes two prompts (diagnose_failed_webhooks, usage_review) and three resources — smsone://guide/agent, smsone://reference/permissions, smsone://reference/webhook-events — so an agent can load the ground rules without leaving the protocol.
