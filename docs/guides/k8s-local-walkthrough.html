Local Kubernetes · k3s · a hands-on walkthrough

Your app, running on a real cluster — on your laptop

We took the Spring modulith + API gateway and ran it on Kubernetes (k3s) inside an Ubuntu VM on your Mac — three copies of the app behind one edge, real database, real login server. Then we broke things on purpose and watched it stay up. This page explains every moving part, assuming you've never touched Kubernetes.

01 — VocabularyThe words first (the only Kubernetes jargon you need)

Kubernetes has a lot of nouns. Here are the seven that appear on this page. Read these once; everything after will click.

Pod

One running container (here: one copy of the app). The smallest thing Kubernetes runs. Pods are disposable — they die and get replaced.

Deployment

A rule that says "keep N identical pods alive." Want 3 copies? The Deployment makes and heals them. Change the image and it rolls pods over one by one.

Service

A stable in-cluster address + built-in load balancer for a set of pods. You talk to modulith:8080; it spreads traffic across the 3 pods for you.

Ingress

The front door. Maps a hostname (api.smsone.local) from outside the cluster to a Service inside it. Ours is Traefik, which ships with k3s.

ConfigMap

Non-secret config (files, settings) handed to pods. We use it to inject the Keycloak realm and the SeaweedFS config.

Secret

Like a ConfigMap, but for passwords/keys. The DB password and the gateway↔app shared secret live here.

Namespace

A folder that groups related objects. Everything of ours lives in the smsone namespace.

Mental shortcut

Deployment = "how many + which image", Service = "how to reach them + load-balance", Ingress = "how the outside world reaches a Service." Almost everything below is just those three, plus config.

02 — TopologyThe big picture: where everything lives

Your Mac runs the tools (kubectl, helm, docker). The cluster runs inside an Ubuntu VM. A request enters through Traefik, hits the gateway, and the gateway forwards to one of three app pods. State (database, cache, files, login) lives in the cluster too.

Two important design choices are visible here:

  • Load balancing is Kubernetes' job. The gateway forwards to http://modulith:8080 — one address. Behind it, Kubernetes' Service fans out to all 3 pods. Add pods and they join automatically.
  • State runs in the cluster too. Locally we deploy Postgres, Valkey, SeaweedFS and Keycloak as pods so the whole thing is self-contained — a production chart would point at managed versions instead.

03 — Build-outThe setup, step by step

Four phases, each with a checkpoint ("gate") we had to pass before moving on. This is exactly what ran.

Phase 0 — a cluster + a way to ship images

k3s is a tiny, complete Kubernetes. Installing it on the VM gives us the whole machine: the container runtime, Traefik (ingress), CoreDNS (in-cluster DNS), storage, and metrics — one command.

Then we point the Mac's kubectl at it (copy the cluster's config, rewrite the address to the VM's IP). Now kubectl get nodes works from the Mac.

The app has to become container images the cluster can run. We build them on the Mac and stream them straight into the VM's image store over SSH — no image registry needed:

Why not a registry?

The plan called for a local image registry (the prod-like way). In practice, streaming the images directly was simpler and needs zero extra infrastructure — so that became the default, with the registry kept as a documented alternative. The app then runs with imagePullPolicy: Never (use the image already on the node).

Phase 1 — the supporting cast (database, cache, files, login)

Before the app can start, its dependencies must exist. We applied plain Kubernetes files that create Postgres, Valkey, SeaweedFS, and a Keycloak (the login/token server) — each as a Deployment + a Service. The checkpoint: a login token minted here carries the right issuer, and the cluster can reach Keycloak by the same name the browser uses. (That's the trick in section 5 — the single most failure-prone step.)

Phase 2 — the app, via a Helm chart

Helm is a package manager for Kubernetes: one chart (a bundle of templates) plus a values file (your settings). We reused the production chart and added a small values-local.yaml that points it at the in-cluster database/cache/login and asks for 3 app copies.

The point of Kubernetes: survive change without downtime. We proved three behaviours (section 7): a rolling upgrade, a pod being killed, and scaling — all while a request loop hammered the app.

04 — Request pathOne request, traced end to end

Here is exactly what happens when you ask for /api/v1/me. Two separate concerns: getting a token (proving who you are) and using it (the actual API call).

Why two checkpoints? The gateway rejects junk early and cheaply, so bad traffic never reaches the app. The app never trusts the gateway blindly — it validates the token again itself. Either layer alone would work; together they're robust.

05 — The tricky bitThe issuer trick (why tokens validate on both sides)

This is the part that trips everyone up, so it gets its own diagram. A login token contains an issuer (iss) — the URL of who minted it. Everyone who checks the token must agree on that URL. The problem: "the browser" and "a pod inside the cluster" reach Keycloak by different paths.

Concretely: Keycloak is told its public name is auth.smsone.local, so it stamps that into every token. On the Mac, /etc/hosts sends that name to the VM's Traefik. Inside the cluster we add a small CoreDNS rule that rewrites the same name to the Keycloak Service. Now the gateway (checking signatures) and the modulith (checking the issuer) both use auth.smsone.local and everything lines up.

If you skip this

Without the CoreDNS rewrite, the app inside the cluster can't resolve auth.smsone.local, or resolves it to something with a different address, and every token is rejected with a confusing "issuer mismatch." It's the #1 local-Kubernetes-with-OIDC footgun.

06 — War storiesTwo bugs I hit (and what they teach)

Real deployments hit snags. Both of these are common Kubernetes lessons, so they're worth understanding rather than just fixing.

Bug 1 — the app crash-looped on startup

The very first rollout crashed with a baffling error:

Kubernetes has a legacy feature: for every Service in the namespace, it injects Docker-style environment variables into your pods — including VALKEY_PORT=tcp://10.43.…:6379 (because there's a Service named valkey). The app reads an env var also called VALKEY_PORT, expecting the number 6379 — and got a URL instead. Boom.

The fix — one line

Set enableServiceLinks: false on the pods. The app finds everything by DNS name anyway (valkey, modulith), so those legacy variables are pure downside. This also protected GATEWAY_PORT from the same collision.

Bug 2 — the chart's settings didn't match the app

The Helm chart was setting environment variables the app no longer reads — BACKEND_URI, GATEWAY_REDIS_HOST, GATEWAY_JWKS_URI — while the app actually wanted MODULITH_URI, VALKEY_HOST, KEYCLOAK_JWKS. The gateway would have started but been unable to reach the app or verify tokens. It also never set the gateway's own port.

07 — The payoffProving zero downtime

We started a loop firing requests through the edge, then upgraded the app to a new image version while it was serving traffic. Kubernetes never lets the count of healthy pods drop.

The load generator's final tally, across the rolling upgrade plus a deliberate pod kill plus scaling 3→5→3:

The other two "production feeling" behaviours came for free from the same machinery:

  • Self-healing: delete a pod and the Deployment immediately creates a replacement; the Service stops sending traffic to the dying one. You lose a pod, not a request.
  • Scaling: kubectl scale --replicas=5 and two more pods join the Service and start taking load within a minute; scale back to 3 just as easily.

09 — TakeawaysThe mental model to keep

  • You declare the desired state; Kubernetes makes it true. "I want 3 copies of this image." It creates them, heals them, and rolls them over on change — you never manage individual pods.
  • Talk to Services, never pods. Pods come and go; the Service is the stable address that load-balances across whatever pods currently exist. That's what makes scaling and healing invisible to callers.
  • Zero downtime = rolling updates + readiness probes. New pods must prove they're ready before old ones leave. The healthy count never dips.
  • Config and secrets are injected, not baked in. The same image runs locally and in prod; only the ConfigMaps/Secrets/values differ.
  • Names must be consistent across the boundary. The issuer/CoreDNS trick is the local expression of a universal rule: everyone must agree on the same hostnames.
The one-sentence version

Kubernetes turned "run this app" into "keep this app running, correctly, through change" — and we proved it with 699 requests and zero failures.
