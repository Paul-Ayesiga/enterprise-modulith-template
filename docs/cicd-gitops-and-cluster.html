CI · CD · GitOps · cluster ops — how the pieces fit

From a commit to a running cluster — and where each tool belongs

Jenkins, Argo CD and Rancher get lumped together as "DevOps tools," but they live in three different stages of the same journey. Here's what each one is, where it sits, and exactly how it maps onto this platform — which already has a working CI pipeline.

Jenkins skip

CI automation server. You already do this with GitHub Actions — adding Jenkins duplicates it.

Argo CD adopt next

GitOps delivery. Turns "commit to Git" into "deployed" and completes your deferred GitOps item.

Rancher later

Cluster management UI. Great once you run several clusters; overkill for one local k3s today.

01 — OrientationThe lifecycle map: three stages, three jobs

The single most useful idea: these tools don't compete (mostly) — they occupy different stages. CI builds and tests. CD deploys. Cluster management operates the clusters. Jenkins and GitHub Actions fight over the CI slot; Argo CD owns CD; Rancher owns the ops layer.

02 — BaselineWhat you already have (so we don't reinvent it)

Your .github/workflows/ci.yml is already a solid Stage-1 pipeline. Knowing this is what makes the Jenkins verdict easy and shows exactly where Argo CD plugs in.

CI job (GitHub Actions)What it does
backend-testsRuns :test and :gateway:app:test (real Testcontainers)
portal-buildBuilds the two Next.js portals (matrix)
supply-chainSBOM (Anchore) + vulnerability scan (Trivy)
helm-lintLints the Helm chart
publish-imagesBuildpacks images → pushes to GHCR (SHA tag + moves :main)
deployA stub — it just echoes a helm upgrade and waits for a cluster credential
The gap

Everything up to "push image to GHCR" works. The last mile — actually getting that image running on a cluster — is a placeholder. That last mile is precisely what Argo CD fills, without ever handing cluster credentials to CI.

03 — Stage 1 (CI)Jenkins — the veteran build server

What
Self-hosted CI/CD automation server
Stage
CI (build & test)
Model
You run the server + agents; pipelines in a Jenkinsfile
For you
Redundant with GitHub Actions

Jenkins is the original open-source automation server: you define a pipeline (checkout → test → build image → scan → push → deploy), and Jenkins runs it on machines you operate, with a vast plugin ecosystem. It's powerful and battle-tested, but you host and maintain the server, the agents, and the plugins.

How it would apply here: a Jenkinsfile could run your Gradle tests, build the buildpacks images, run Trivy, push to a registry, and call helm upgrade — i.e. re-implement what ci.yml already does for free on GitHub's runners.

Verdict — skip (for now)

You already have a complete CI pipeline in GitHub Actions. Adding Jenkins means a server to babysit and a duplicate pipeline. Only choose Jenkins if you need self-hosted / air-gapped CI (compliance, on-prem, no cloud runners) or your org already standardizes on it. Otherwise it's motion without progress.

04 — Stage 2 (CD)Argo CD — Git becomes the deploy button

What
GitOps continuous delivery for Kubernetes
Stage
CD (deploy)
Model
Runs inside the cluster; pulls desired state from Git
For you
The natural next step

Argo CD runs inside your cluster and continuously makes the cluster match what's declared in a Git repo — your Helm chart plus a values file. Git is the single source of truth. Change the desired image tag in Git, and Argo notices and syncs. It shows you a live diff (Git vs cluster), auto-heals drift (someone kubectl edits something? it reverts), and gives a clean web UI + history.

How it maps onto this repo: you'd create one Argo "Application" pointing at deploy/helm/smsone with a prod values file. Then:

  • Your CI's deploy stub goes away — no KUBECONFIG secret in GitHub, because Argo pulls from inside the cluster (a big security win).
  • "Deploying" becomes: CI pushes the image to GHCR, then bumps the image tag in Git → Argo syncs it.
  • The zero-downtime rolling update you already saw is unchanged — Argo just runs the same Helm release, so Kubernetes still does surge-then-terminate.
Verdict — adopt next

Biggest value for least effort, and it completes the GitOps item explicitly deferred in docs/K8S_LOCAL_PLAN.md §8. It installs on your existing local k3s in a couple of minutes, so it's also the best way to learn GitOps hands-on. (Flux is the main alternative — same idea, no UI, more CLI.)

Now running on your cluster

Argo CD is installed on the local k3s and syncing deploy/helm/smsone: a git push that changed modulith.replicas scaled the Deployment with no kubectl and no helm — and Argo reverted an earlier manual --set back to what Git said. Reproduce with make k3s-argocd; open the UI via kubectl -n argocd port-forward svc/argocd-server 8080:80.

05 — Stage 3 (Ops)Rancher — one pane of glass over many clusters

What
Kubernetes management platform (SUSE)
Stage
Cluster ops / management
Model
A control plane + web UI over one or many clusters
For you
Useful as you add environments

Rancher is a management platform: a web UI and control plane to provision, secure (centralized RBAC / SSO), monitor and operate many Kubernetes clusters from one place. It includes an app catalog, cluster provisioning, monitoring, and its own GitOps engine (Fleet). It does not build or deploy your app — it manages the clusters your app runs on. (Fun fact: k3s, the cluster you're already running, is a Rancher/SUSE project.)

Don't confuse the two

Rancher (the server platform, this section) is not Rancher Desktop (a laptop app for running containers/k8s locally, in the same space as Docker Desktop). Different products, same brand.

How it would apply here: install Rancher and you get a GUI over your k3s — browse pods, read logs, scale, and manage access without kubectl. The real payoff arrives when you have several clusters (local → dev → staging → prod): manage them all, with unified users and policies, in one UI.

Verdict — later / optional

Overkill for a single local cluster today. Reach for it when you have multiple clusters or teammates who want a UI instead of the CLI. Argo CD (Stage 2) delivers more value first.

06 — Putting it togetherThe target pipeline for this platform

Wire the tools to their stages and the whole path from keyboard to cluster becomes hands-off and auditable — every change is a Git commit.

Notice there's no arrow from CI straight into the cluster: CI's job ends at "push image + commit the new tag." Argo takes it from there. That separation is the heart of GitOps — and why no cluster password ever lives in CI.

07 — The runtimeInside the Ubuntu server: where things actually live

A frequent surprise for people new to Kubernetes: you don't copy your app or files onto the server. The YAML, scripts and values-local.yaml live in the Git repo on your Mac. You tell the Kubernetes API "run this," and it schedules containers from images. So the VM has no project folder to browse — it holds images, live data, and a database of objects.

WhatWhere on the VMHow you're meant to look
App imagescontainerd store (not plain files)sudo k3s ctr images ls | grep smsone
Persistent data (DB rows, uploaded files)/var/lib/rancher/k3s/storage/ → pvc-…_smsone_postgres-data, …_seaweedfs-dataroot-owned; read it through the app
The objects you applied (Deployments, Services, ConfigMaps, Secrets)/var/lib/rancher/k3s/server/db/state.db — a SQLite database, not filesnever edit directly — use kubectl
Cluster credentials/etc/rancher/k3s/k3s.yamlalready copied to ~/.kube/smsone-k3s.yaml on the Mac

The mental model: the repo (Mac) is the source of truth for what runs; the VM is a runtime holding images + live data + an object database, all managed through kubectl — not by browsing directories. The right way to "see the contents":

Why Postman said ENOTFOUND api.smsone.local

api.smsone.local is a made-up name that no DNS server knows. Your Mac must be told where it points — add <VM-IP> api.smsone.local auth.smsone.local to /etc/hosts, then restart Postman (it caches DNS). Inside the cluster this "just works" because CoreDNS resolves the names — which is why the proof ran from within the cluster.

08 — RecommendationWhat to adopt, in order

  1. Now — nothing to add. GitHub Actions already gives you tests, SBOM/scan, and images in GHCR.
  2. Next — Argo CD (GitOps). Install it on the existing k3s, point one Application at deploy/helm/smsone, enable auto-sync. Replace the CI deploy stub with a tag-bump commit. This completes the deferred GitOps item and removes cluster credentials from CI.
  3. Later — as you scale. Rancher when you run multiple clusters or want a UI for non-CLI folks; optionally Argo Rollouts for canary/blue-green on top of Argo CD.
  4. Skip — Jenkins, unless a hard self-hosted/on-prem CI requirement appears.
