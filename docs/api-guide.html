SMSOne · API Guide for Testers
Swagger UI OpenAPI

How to read this. Every endpoint is one block: the method, the path, and — on the right — who can call it. Access runs on two disjoint axes, so the chip tells you which one and never mixes them:

any caller — any signed-in user, for their own data (the Shared axis) platform-admin — a Keycloak realm role (support → admin → superadmin) member:invite — an organization permission, inside one tenant

A platform role grants zero org permissions and vice-versa — the only sanctioned crossing is impersonation. Paths use {orgId} for the tenant id.

A · Before you call anything

The five things true of every request: how you authenticate, the shape you always get back, how lists page, how you get rate-limited, and how to make writes safely retryable.

A1 · Authentication & the two axes

Every call carries a Keycloak bearer token minted for this API (audience smsone-api). Dev shortcut: make token or scripts/api.sh (which also encodes page[...] for you).

# raw password grant (dev realm) → an access token
curl -s $BASE/realms/smsone/protocol/openid-connect/token \
  -d grant_type=password -d client_id=smsone-web \
  -d username=paul -d password=Paul123 | jq -r .access_token

# then send it on every call
curl $BASE/api/v1/me -H "Authorization: Bearer $TOKEN"
Machine access uses X-Api-Key: <prefix>.<secret> instead of a bearer (see Org API keys). Impersonation adds X-Impersonate: <sessionId> to a tenant call (see Users & impersonation). Never combine axes in one credential.
Org-scoped tokens. Tenant calls need the token's Keycloak organization claim to name the org in the path — a token scoped to org A gets 403 on org B even if you belong to both. Switching orgs = requesting a new token scoped to the other; the server never trusts a client-asserted active org.

No-JIT: a valid JWT alone is not access — the subject also needs a provisioned app_user row, or you get 403 ACCOUNT_NOT_PROVISIONED. GET /api/v1/me is the one gate exception (so you can see your own onboarding status).

A2 · The response envelope & errors

Every JSON response is one envelope — data xor errors, always meta.requestId (also the X-Request-Id header; quote it in bug reports).

{ "data": { "id": "org.example", "type": "setting", "attributes": { "key":"org.example", "value":"42" } },
  "meta": { "requestId": "01J4X9GVJ4C1T4V0V3S8B7NQZD" } }

{ "errors": [ { "status":"422", "code":"VALIDATION_FAILED", "title":"Validation failed",
                "detail":"cron must be a valid six-field Spring cron expression.",
                "source": { "pointer":"/data/attributes/cron" } } ],
  "meta": { "requestId": "01J4X9…" } }
  • Prefer RFC 9457? Send Accept: application/problem+json — same data, standard shape.
  • Localized details: send Accept-Language: fr; when the catalog holds error.<code> the detail localizes, else you get the English original.
  • Stack traces never reach the wire — a 500's detail is generic; the trace lives in the server log under your request id.

A3 · Cursor pagination

Collections page by keyset cursor — no page numbers, no totals (by design). Parameters are literally page[size] and page[after] (encode the brackets, or let scripts/api.sh do it).

ParamInReqDescription
page[size]querynoRows per page (default 20). No total count is ever returned.
page[after]querynoOpaque cursor from a previous page's meta.page.nextCursor / links.next.
GET /api/v1/orgs/{orgId}/exchange/jobs?page[size]=2
  "meta": { "page": { "size":2, "count":2, "hasMore":true, "nextCursor":"Y3JlYXRlZEF0P…" } },
  "links": { "next": "…?page[size]=2&page[after]=Y3JlYXRlZEF0…" }

Follow links.next until hasMore is false. Cursors are opaque and collection-specific — replaying one against another collection is a 422, not a 500.

A4 · Rate limits & plan quotas

There are two rate controls in front of you, at different layers, protecting different things. Both answer 429, but for different reasons — so they speak through different headers, and the right response to each is different. Don't confuse them.

 Edge burst limiterPlan quota
The question“Are you spiking too fast, right now?”“Have you used what your plan entitles you to?”
PurposeInfrastructure protection / burst-smoothing — stop any one caller from slamming the front door.Commercial fairness — enforce the volume your subscription buys, shared fairly across tenants.
UnitRate over seconds — a token bucket, ~20 req/s sustained, 40 burst.Volume over a window — e.g. 600 reads/min, 60 writes/min (per your plan).
ScopePer caller (principal → tenant → IP), applied to everyone.Per organization, tied to your subscription tier.
HeadersX-Edge-RateLimit-Remaining · -Burst-Capacity · -Replenish-RateX-RateLimit-Limit/Remaining/Reset + draft-IETF RateLimit / RateLimit-Policy
On 429, doSlow your request rate. Back off and retry after Retry-After.Upgrade the plan, or wait for the window. Envelope RATE_LIMITED + Retry-After.

They're deliberately kept apart — defense in depth: a caller comfortably inside their plan still can't fire thousands of requests in one second (the edge bucket stops that), and a caller under the edge burst still can't exceed the plan's per-window allowance (the quota stops that). The namespaced headers are what let your client tell which limit it hit.

# A normal 200 through the gateway carries BOTH sets — they never collide:
X-RateLimit-Limit: 600     X-RateLimit-Remaining: 599     RateLimit: "read";r=599;t=60     ← plan quota
X-Edge-RateLimit-Remaining: 39     X-Edge-RateLimit-Burst-Capacity: 40                      ← edge burst bucket

# Edge burst 429 — you sent a spike; slow down (retry in a second):
HTTP/1.1 429     Retry-After: 1     X-Edge-RateLimit-Remaining: 0

# Plan quota 429 — you used your plan's allowance; upgrade or wait for the window:
HTTP/1.1 429     Retry-After: 30     RateLimit: "read";r=0;t=30
{ "errors": [ { "code":"RATE_LIMITED", "detail":"Rate limit exceeded for 'read'. Retry after 30s." } ] }
How to react in code. Always honour Retry-After. If you keep hitting the edge limit (X-Edge-RateLimit-*) you're bursting — add client-side pacing / exponential backoff. If you keep hitting the plan quota (X-RateLimit-* / RateLimit) you're at your subscription ceiling — spread the work across the window or upgrade the plan.

Automatic retries (safe methods only)

Separately from rate limiting: when a backend momentarily fails with a 5xx, a route configured for retries has the gateway retry automatically — GET only (attempt 1 → 2 → 3, then it gives up). Writes are never auto-retried: replaying a POST/PUT/DELETE could duplicate a side effect. To make a write safely retryable, send an Idempotency-Key — then a retry replays the stored response instead of running the operation twice.

A5 · Idempotency keys

Any unsafe request may carry Idempotency-Key: <your-uuid>. Same principal + same key + same body ⇒ the stored response replays; same key with a different body ⇒ 409. Keys live 24h.

B · You — anything a signed-in user does for themselves

The Shared axis: no platform role, no org permission — just any caller acting on their own account. This is where every tester starts.

B1 · Who am I

GET/api/v1/meany caller

Your identity, effective roles (already tier-expanded), active org, and provisioning status. The one call that works while INVITED — so you can see your own onboarding.

{ "data": { "id":"5862…", "type":"user", "attributes": {
    "email":"you@acme.test", "roles":["platform-admin","USER","platform-support","platform-superadmin"],
    "activeOrgId":"6a1f…", "activeOrgAlias":"acme", "provisioningStatus":"ACTIVE" } } }

Four roles from two grants: platform-superadmin + USER — the hierarchy expands superadmin → admin → support. It shows your effective tiers, not four separate grants.

POST/api/v1/filesany caller

GET/api/v1/documentsany caller

Your personal document catalog (support may read others', admin may delete). The org-scoped equivalent is under /orgs/{orgId}/documents.

C · Operating the platform

The Platform axis — a Keycloak realm role, hierarchical: platform-support (read) → platform-admin (change) → platform-superadmin (escalate). These surfaces manage tenants and the platform itself, never a tenant's data directly (that's impersonation).

C1 · Tenants — the org lifecycle

POST/api/v1/orgsplatform-admin

Create a tenant + provision its Keycloak org and first OWNER (invite email lands in Mailpit).

C2 · Users & impersonation

GET/api/v1/admin/usersplatform-support

Every identity across every tenant (cursor-paginated); …/{subject}/profile reads one. Note email is not unique here — identity keys on the Keycloak subject, so two accounts can share an email.

POST/api/v1/admin/impersonationsplatform-support

The only sanctioned bridge from an operator to tenant data — and it's audited. Open a session, then repeat your own tenant call with X-Impersonate: <id>. mode:WRITE needs platform-admin.

C3 · Plans, entitlements, trials & billing

How Kill Bill fits — the mental model. Kill Bill is a separate billing engine (its own container); the app hands it the money side and reads results back. Mind the word tenant: in Kill Bill it means a whole isolated billing world — not your org. Your entire platform is one Kill Bill tenant (smsone); each of your orgs is a Kill Bill account inside it. 
Kill Bill (the container)
 └─ Tenant: smsone           ← your ENTIRE platform — ONE tenant  (api-key smsone / secret smsone-secret)
     ├─ Catalog              ← the plans you sell (pro-monthly, enterprise-monthly); no catalog ⇒ nothing to subscribe to
     ├─ Account: acme        ← your org "acme" — one Kill Bill account per org
     │    └─ Subscription    ← acme on "pro-monthly"  →  Invoices / Payments
     └─ Account: globex …
Two credentials, easily confused: admin/password logs into the Kaui console; smsone/smsone-secret (api-key/secret) selects which billing world — and the app authenticates with that same pair. Kill Bill owns the money (invoices, balances); the app's entitlements stay the authority for what a plan lets an org do. Kill Bill events reconcile into entitlements — the one write direction. Turn on app.billing.auto-provision-accounts (or run make killbill-init then create an org) and a new org lands as an account here automatically.
GET/api/v1/admin/plansplatform-support

The plan catalog, rank-ordered. Entitlement encoding: -1 = feature on, a positive number = a cap, an absent key = off / unlimited.

POST/api/v1/admin/plans · PUT …/{code} · DELETE …/{code}platform-admin

Full catalog CRUD. Create/update take {code,name,rank,entitlements}; send null (or -1) for feature-on, a number for a cap, omit for off. Deleting FREE or an in-use plan ⇒ 409.

POST /api/v1/admin/plans {"code":"scale","name":"Scale","rank":5,"entitlements":{"exchange.enabled":null,"members.max":500}}
PUT/api/v1/admin/orgs/{orgId}/subscriptionplatform-admin

Assign a tenant's plan (audited). Bites the next request (cache evicted) and fans out org.subscription_changed. A trial: POST …/subscription/trial {"plan":"PRO","days":14}.

PUT …/subscription {"plan":"PRO"}   # gate refusals are UPGRADE-shaped, before side effects:
403 {"detail":"Your plan allows 25 for 'members.max' and that limit is reached. Upgrade the plan to add more."}

Standings: ACTIVE/TRIALING = full access · PAST_DUE = grace (entitlements kept) · PAUSED = READ-ONLY (org writes answer 402 SUBSCRIPTION_PAUSED). A lapsed trial pauses automatically.

POST/api/v1/admin/orgs/{orgId}/billing/…platform-admin

Kill Bill (billing system of record) — link an account, drive a KB subscription, read balance + methods. Entitlements above stay the single authority; billing events reconcile into them. Raw card data never touches this API.

How billing connects — the platform-manages-tenant model. Kill Bill's own tenant is the whole platform: one shared tenant, the smsone api-key/secret that both the app and Kaui authenticate with. Each of your orgs is a Kill Bill account inside that one tenant — so the platform runs a single KB tenant and manages every org as an account under it. To make data appear (e.g. in Kaui):
  1. Boot with BILLING_BOOTSTRAP=true — the app runs ensureTenant() and uploads the plan catalog (pro-monthly, enterprise-monthly).
  2. POST /api/v1/admin/orgs/{orgId}/billing/account — create that org's KB account (idempotent).
  3. POST /api/v1/admin/orgs/{orgId}/billing/subscription {"plan":"PRO"} — KB starts the subscription and cuts the first invoice.
  4. See it in Kaui (Accounts → the org) or via GET /api/v1/orgs/{orgId}/billing/invoices. Set BILLING_CALLBACK_URL so KB pushes invoice/payment events back and the standing reconciles (PAST_DUE ↔ ACTIVE).
The money edges run themselves. A failed Kill Bill payment marks the org PAST_DUE; the nightly dunning job pauses any org past-due longer than the grace window (app.billing.dunning.grace-days, default 7) — and both transitions email the org's owners. A later successful payment (Kill Bill event or a completed D5 collection) lifts the standing back to ACTIVE and sends a best-effort receipt (latest-invoice summary). Metered usage: the gateway reports each org's daily API request counts into the api_usage_daily ledger (internal seam, X-Gateway-Secret-signed); with app.billing.usage-export.enabled=true the nightly export pushes them to Kill Bill as api-requests usage (tracking-id-deduped) for usage-based plans.

C4 · Support queue, SLA, compliance & retention

GET/api/v1/admin/ticketsplatform-support

The cross-tenant support queue. Assign (…/{id}/assignment), reply public or internal:true (…/{id}/messages), set status (PUT …/{id}/status). SLA breaches auto-escalate + fire org.ticket.escalated. Per-priority SLA overrides live at …/admin/orgs/{orgId}/sla/{P1..P4}.

POST/api/v1/admin/compliance/legal-holds/subjectplatform-admin

A legal hold BLOCKS the purge and any erasure of the held subject/org until released (DELETE …/legal-holds/{id}). POST …/compliance/erasure {"subject":"…"} erases on behalf of a subject — REFUSED under a hold or for the last super-admin.

PUT/api/v1/admin/orgs/{orgId}/retention/{scope}platform-admin

Keep one org's log rows on a different schedule than the default. {scope} ∈ webhook-delivery, exchange-job (the only org-scoped logs). {"days":365}; DELETE reverts to default.

GET/api/v1/admin/compliance/orgs/{orgId}/exportplatform-admin

One organization's data as a single JSON bundle — offboarding and DSAR handovers. Reads across every org-owned table (memberships, roles, subscriptions, webhooks + deliveries, payments, usage, exchange, documents, tickets, audit …); secret-bearing columns (webhook secrets, API-key hashes) are dropped at the source; capped at 1000 rows per table (the cap is stated in the payload). The export itself is audited.

GET /api/v1/admin/compliance/orgs/{orgId}/export
# → {"attributes":{"organizationId":"…","rowCapPerTable":1000,"tables":{"organization":[…],"membership":[…],…}}}

C5 · Platform config — integrations, settings, maintenance, ops

PUT/api/v1/admin/integrationsplatform-admin

The platform-default provider for a kind (SMS_PROVIDER, EMAIL_PROVIDER, PAYMENT_GATEWAY) — used by any org without its own override. Secret settings are encrypted + masked on read.

PUT/api/v1/settings/{key} · /api/v1/feature-flags/{key} · /api/v1/translations/{locale}/{key}platform-admin

Write platform reference data (any caller reads it — B4). Translations power Accept-Language error details.

PUT /api/v1/settings/branding.name          {"value":"SMSOne"}
PUT /api/v1/translations/fr/error.forbidden {"value":"Accès refusé."}
PUT/api/v1/feature-flags/{key}/orgs/{orgId}platform-admin

Flag targeting. Precedence per org: org override (this endpoint — pins hard ON/OFF) → percentage rollout (percentage: 0–100 on the flag's own PUT; deterministic per-org bucket, sticky, only widens an enabled flag) → the global value. DELETE clears the override; GET …/{key}/orgs/{orgId} (also org:read) answers what that org effectively gets — unknown flags evaluate false, never an error.

PUT /api/v1/feature-flags/beta.exports        {"enabled":true,"percentage":25}   # 25% of orgs, sticky
PUT /api/v1/feature-flags/beta.exports/orgs/{orgId} {"enabled":true}              # this org: always on
GET /api/v1/feature-flags/beta.exports/orgs/{orgId}   # → {"type":"feature-flag-evaluation","attributes":{"enabled":true}}
POST/api/v1/admin/maintenanceplatform-admin

Schedule a window (orgId:null = platform-wide). In a RESTRICT window an org's writes answer 503 Retry-After (reads pass); ANNOUNCE is banner-only. Distinct from suspending a tenant (that's permanent).

POST /api/v1/admin/maintenance {"mode":"RESTRICT","message":"DB upgrade","startsAt":"…","endsAt":"…"}
GET/api/v1/admin/scheduler/locks · /api/v1/analytics/reportsplatform-support

Ops observability — clustered-job lock rows, and the curated analytics report catalog (run one: …/reports/{code}). Platform API keys (support-tier, read-only) live at /api/v1/admin/api-keys.

D · Inside an organization

The Organization axis — a permission the token carries for this tenant (member:invite, webhook:manage, …). Every path is under /api/v1/orgs/{orgId}/… and needs the token scoped to that org.

D1 · Members, roles & groups

POST/api/v1/orgs/{orgId}/membersmember:invite

Invite someone (provisions identity + temp creds, emailed). Idempotent re-invites return the existing membership.

FieldTypeReqDescription
emailstringyesInvitee. Reused if a Keycloak account already has it.
firstName / lastNamestringnoOn the invite.
roleCodestringyesA role that exists in this org (mint it first — unknown ⇒ 404).
POST /api/v1/orgs/{orgId}/members {"email":"jo@acme.test","firstName":"Jo","roleCode":"MEMBER"}
POST/api/v1/orgs/{orgId}/rolesrole:create

A custom role; permissions are exact names from the catalog. Reassign a member with PUT …/members/{subject}/role; remove with DELETE …/members/{subject} (last-owner protected ⇒ 409).

POST /api/v1/orgs/{orgId}/roles {"code":"AUDITOR","name":"Auditor","permissions":["org:read","audit:read"]}
POST/api/v1/orgs/{orgId}/groupsmember:role:assign

A group confers ITS role to every member on top of their own (permissions UNION); add members (…/{id}/members {"subject":"…"}), remove to drop the conferred permissions. Effect is immediate.

The escalation guard. You can only grant permissions you hold. Inviting into a role carrying member:remove when you lack it ⇒ 403 "You cannot grant permissions you do not hold: member:remove". The same rule guards exchange imports, evaluated against the requester at processing time.

D2 · API keys (machine access)

POST/api/v1/orgs/{orgId}/api-keysapikey:manage

Mint a machine key carrying a subset of your permissions (never more). The full secret is shown once. Use it as X-Api-Key: <prefix>.<secret> instead of a bearer. DELETE …/{id} revokes (next call 401s); POST …/{id}/rotate replaces it atomically.

POST /api/v1/orgs/{orgId}/api-keys {"name":"ci-bot","permissions":["org:read","member:read"]}

D3 · Webhooks (outbound events)

POST/api/v1/orgs/{orgId}/webhookswebhook:manage

Subscribe a URL to events (browse the vocabulary at GET /api/v1/webhooks/event-types). The signing secret is shown once. Delivery is at-least-once with backoff → dead-letter after 5 tries; per-subscription log at …/webhooks/{id}/deliveries.

POST /api/v1/orgs/{orgId}/webhooks {"url":"https://hooks.acme.test/smsone","events":["org.member.added"]}
# each delivery: header  X-Webhook-Signature: sha256=88e2c4…  — HMAC-SHA256 over the EXACT raw body with your secret
echo -n "$RAW_BODY" | openssl dgst -sha256 -hmac "$WHSEC" -hex   # must equal the header
POST/api/v1/orgs/{orgId}/webhooks/{id}/rotate-secretwebhook:manage

Mint a fresh signing secret for one subscription (compromise response / scheduled hygiene). Same secret-once semantics as create — the new whsec_… appears in this response only. Order matters: deploy the new secret to your receiver first, then rotate — deliveries sign with the new secret immediately, and a receiver still validating the old one will reject them (they retry with backoff, so a short overlap self-heals). Audited.

POST /api/v1/orgs/{orgId}/webhooks/{id}/rotate-secret
# → 200 {"attributes":{"secret":"whsec_1c9e…full…"}}     ← store it NOW; reads stay masked

D4 · Exchange — imports & exports at scale

Import/export is jobs, never long requests (CSV/JSONL/XLSX/XML). Submitting needs the handler's own permission (e.g. org-members import needs member:invite).

POST/api/v1/orgs/{orgId}/exchange/imports?handler=&format=handler's permission

Discover handlers + template, then submit (multipart file) → 202 with a job id. Poll the job; a crashed run resumes from its last committed batch (at-least-once into idempotent handlers).

GET  /api/v1/exchange/handlers                                   # importPermission, header, formats
GET  /api/v1/exchange/handlers/org-members/template?format=CSV  # ready-to-fill
curl -X POST "$BASE/api/v1/orgs/{orgId}/exchange/imports?handler=org-members&format=CSV" -F file=@members.csv
# → 202 job; then:
GET  /api/v1/orgs/{orgId}/exchange/jobs/{jobId}          # {"status":"COMPLETED_WITH_ERRORS","processed":2,"failed":1}
GET  /api/v1/orgs/{orgId}/exchange/jobs/{jobId}/report   # 302 → row-addressed CSV: row_number,error
GET  /api/v1/orgs/{orgId}/exchange/jobs/{jobId}/result   # 302 → the output file (exports)
POST/api/v1/orgs/{orgId}/exchange/scheduleshandler's permission

A recurring export (six-field Spring cron, UTC) — fires AS you; revoking your permission disables it.

POST …/exchange/schedules {"handler":"org-members","format":"CSV","cron":"0 0 2 * * *"}

D5 · Billing & payment collection

GET/api/v1/orgs/{orgId}/billing/invoices · /payment-methodsorg:read

The tenant's own invoices + subscription view. Add a payment method (POST …/payment-methods, org:update) — also the pay-to-recover path out of a PAUSED standing. Raw card data never touches this API; pluginProperties carries only what a hosted page tokenized.

POST/api/v1/orgs/{orgId}/paymentsorg:update

Initiate a payment collection through a gateway. provider is optional — omitted, the org's configured PAYMENT_GATEWAY integration names it (org override → platform default), so which PSP serves an org is configuration, not caller knowledge. Every gateway runs in a switchable sandbox/live mode, echoed on the resource — nothing touches real money until live is explicit.

FieldTypeReqDescription
providerstringnopesapal (hosted page: card + mobile money) or yo-uganda (mobile-money prompt pushed to the handset). Default: the org's configured gateway.
amountnumberyesPositive; charged in currency.
currencystringyes3-letter ISO, e.g. UGX.
descriptionstringyes≤100 chars — appears on the payer's page/statement.
phoneNumber / emailstringoneThe payer's contact. Yo! requires the phone (that handset gets the approval prompt).
POST /api/v1/orgs/{orgId}/payments
{"provider":"pesapal","amount":15000,"currency":"UGX","description":"PRO plan invoice","email":"payer@acme.test"}
# → 201 {"attributes":{"status":"PENDING","mode":"sandbox","redirectUrl":"https://cybqa.pesapal.com/…",
#                      "amount":15000,"vatAmount":2288.14,"netAmount":12711.86}}
#   pesapal: send the payer to redirectUrl · yo-uganda: no redirect, the prompt is on the phone

With TAX_VAT_RATE set (e.g. 18) the quoted amount is treated as VAT-inclusive and the response echoes the breakdown — vatAmount = amount×r/(100+r), netAmount the rest — for the receipt/ledger. The payer is always charged exactly amount.

GET/api/v1/orgs/{orgId}/payments/{id}org:read

Read-with-refresh: a PENDING payment re-asks its gateway before answering (this is how Yo!'s poll flow completes), so poll this until the status is terminal — COMPLETED / FAILED / REVERSED never regress. The gateway's own answer is the only truth: Pesapal's public IPN + browser callback (/api/v1/payments/pesapal/ipn·/callback, unauthenticated by vendor design) are inert triggers that just cause the same server-side re-query.

GET …/payments/{id}   # → {"status":"COMPLETED","confirmationCode":"…","statusDetail":"Completed via MpesaUG"}

A collection reaching COMPLETED is money in: it lifts a PAST_DUE/PAUSED standing back to ACTIVE on the spot — the payments surface stays reachable while paused, so this is the self-service way out of read-only (the C3 dunning card is the way in).

D6 · Security policy & integrations

PUT/api/v1/orgs/{orgId}/security-policyorg:update

Tighten how the org is reached — each field optional, each tightens. A block is a 403 that names the rule ("Blocked by your organization's security policy (trusted-device)."), never confusable with RBAC. You can never lock yourself out of /security-policy itself.

PUT …/security-policy {"ipAllowlist":"203.0.113.0/24","requireTrustedDevice":true,
                       "sessionMaxAgeSeconds":3600,"requireMfa":true}
POST …/security-policy/trusted-devices {"subject":"kc-7d2e…","deviceId":"…","trusted":true}   # trust is the org's grant

ipAllowlist judges the real client, not the proxy in front: the platform declares its proxy depth (TRUSTED_PROXY_HOPS — 0 direct, 1 behind the gateway, 2 behind ingress + gateway) and only the proxy-vouched X-Forwarded-For entry is believed; a caller-forged entry buys nothing. Platform-wide IP blocking is separate and earlier — the gateway's deny-list refuses hostile sources before authentication.

requireMfa holds human sessions to a multi-factor token — the JWT's amr claim must name a second factor (otp/totp/webauthn…), else 403 (mfa). API keys are machine credentials and exempt; new invites into a require-MFA org get TOTP enrollment added to their first-login link (CONFIGURE_TOTP).

PUT/api/v1/orgs/{orgId}/integrationsorg:update

An org override for a provider kind — wins over the platform default (C5), which wins over env config. This is how orgs opt for different providers: SMS_PROVIDER → speedamobile (settings apiId/apiPassword/senderId; notifications route each SMS by the recipient org's choice) · PAYMENT_GATEWAY → pesapal | yo-uganda (settings include mode: sandbox|live and the gateway credentials; also sets the org's default payment provider, D5). Secrets encrypted + masked; POST …/integrations/{id}/test probes it.

PUT /api/v1/orgs/{orgId}/integrations
{"kind":"PAYMENT_GATEWAY","provider":"yo-uganda","settings":{"mode":"live","apiUsername":"…","apiPassword":"…"}}

D7 · Documents, search, support, audit & maintenance

POST/api/v1/orgs/{orgId}/documentsdocument:manage

Org document catalog (multipart file). GET …/{id} 302s to a presigned URL; DELETE drops the bytes but the metadata row soft-remains (the trail). Exchange artifacts appear here with source:"EXCHANGE".

GET/api/v1/orgs/{orgId}/search?q=org:read

Ranked full-text (with trigram fallback for typos), tenant cut inside the SQL. Platform-wide search is /api/v1/admin/search (platform-support).

POST/api/v1/orgs/{orgId}/ticketsorg:read

Open + converse on your support tickets (…/{id}/messages — public messages only; internal notes hidden). The platform side is C4.

GET/api/v1/orgs/{orgId}/auditaudit:read

Your tenant's own trail; filter action/from/to. Rows written during an impersonation name the operator as actor with onBehalfOf. Read the maintenance banner at GET …/maintenance?active=true.

E2 · Tester tips

  • make run boots app + full stack; make seed adds the acme demo org. Mailpit (:8025) catches invite emails; Grafana (:3000, folder SMSOne) shows the platform's own counters.
  • Async: submits answer 202 — poll the job resource, don't sleep. Webhook / notification deliveries are background workers; the delivery-log endpoints are your observability.
  • Repro reports: always include meta.requestId (and, for exchange, the job id) — every server log line for the run carries both, plus org_id.
  • The whole suite runs on real containers (./gradlew test) — Postgres, Keycloak, SeaweedFS, Valkey, Kill Bill. What passes there behaves the same against the compose stack.
